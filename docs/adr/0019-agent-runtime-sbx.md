# ADR-0019 — Agent runtime: back to Docker Sandboxes (sbx), state on the external volume

**Status:** Accepted · **Date:** 2026-11-20 · **Supersedes:** ADR-0018 §§ 1, 2, 4, 5 · **Keeps:** ADR-0018 § 3 (per-role GitHub Apps) and `mise.toml`

## Context
ADR-0018 moved agents out of sbx because sbx kept its VM disks on the internal drive. sbx now honours a storage root: with `SANDBOXES_STORAGE_ROOT` pointing to a directory on the external volume (exported for login shells and for `launchd`, so the daemon and the CLI agree), every sandbox disk, template and daemon state lives there. That removes the only reason for leaving sbx, and host worktrees had real costs: agents ran as the owner's OS user, the Claude Code sandbox was bypassable through the Docker socket, sessions could read their own App token, and full-stack E2E had to be serialised on shared host ports.

A probe on 2026-11-20 (sbx v0.54.0) confirmed: the daemon runs on the external storage root; the global network policy is `balanced` on top of deny-all; a sandbox-scoped dynamic `github` secret minted for one App authenticates `gh` and `git` over HTTPS through the host proxy; inside the sandbox `GH_TOKEN` holds only a proxy placeholder, never the token; the reviewer App's push is rejected (403) while the implementer App's push succeeds; replacing the secret takes effect without restarting the sandbox.

## Decision
1. **Runtime.** Every agent (planner, implementer, fixer, reviewer) runs in its **own sbx microVM**, created by `scripts/agents/dispatch.sh` from the project template with `--clone` (an in-container clone; the host checkout is mounted read-only as the clone source, so nothing secret may live in it). One task = one sandbox = one branch. The reviewer gets a fresh sandbox per review, removed afterwards; task sandboxes are removed when the PR merges or the task is escalated. sbx state lives under the external volume via `SANDBOXES_STORAGE_ROOT`; nothing is stored on the system drive.
2. **The sandbox is the boundary.** Isolation is the microVM, not Claude Code's in-process sandbox, so inside it `claude -p … --dangerously-skip-permissions < /dev/null` is allowed (and is the only place it is). Each sandbox runs its own Docker daemon (Testcontainers, `make up`, `make e2e`); the host Docker socket is not exposed. Egress follows the global sbx network policy (`balanced`, deny when no rule decides); per-sandbox `sbx policy` rules may narrow it, never widen it without an owner-approved change to this ADR.
3. **Identities and credentials (ADR-0018 § 3 kept, mechanism changed).** The two Apps, their permissions and the rule *each role uses only its own App credential, always* are unchanged. The token reaches a sandbox only as **one sandbox-scoped dynamic secret**: `sbx secret set github --sandbox <name> --command '<helper> <app> -' --refresh 55m`, where the helper mints a ≤ 1 h installation token for that one App from its Keychain key. The proxy injects it into GitHub requests; the agent sees only a placeholder, so it cannot print, store or exfiltrate the token, and no private key, owner login or other role's credential ever enters a sandbox. The helper and any configuration it reads live outside every sandbox mount (sbx requires this; it runs the helper unconfined on the host). This also restores ADR-0016 § 1's "agents never see raw values"; the only GitHub credential-shaped value inside is the placeholder.
4. **Claude authentication** uses the owner's Claude subscription through the sbx proxy's own OAuth handling: the owner runs `/login` once in an interactive sandbox, and the proxy keeps the OAuth credential and injects it on requests to `api.anthropic.com`; no Anthropic credential enters any sandbox. That login has a hard lifetime and cannot be renewed from inside a sandbox, so when it expires the dispatcher must detect the authentication failure (Claude exits with `Not logged in` / an authentication error), stop dispatching, and flag the tracking issue `needs-human`; the owner logs in again and the wave resumes. Rejected: a `claude setup-token` token, because the proxy strips the `Authorization` header on every request to `api.anthropic.com` (a custom placeholder secret or a token placed in the sandbox environment never reaches the API) and the built-in `anthropic` service stores a pasted value as an API key; a Console API key, to keep usage on the subscription. Sandboxes keep the credential state they were created with, so a credential change is verified in a fresh sandbox.
5. **Toolchain.** `mise.toml` stays the single source of versions. The toolchain is an sbx **mixin kit** in the repository (`infra/sbx/varco-toolchain`), layered on the built-in `claude` kit (which keeps its own Docker daemon, proxy login and network rules): its Dockerfile runs a pinned, checksum-verified `mise install` of `mise.toml` at kit build time, and its install hook adds the sbx proxy CA to the JDK trust store and puts the tools on every shell's `PATH`. `make sbx-kit` assembles the kit with its copy of `mise.toml`, because sbx builds a local kit only from its own directory; sbx caches the build, so it reruns only when the kit or `mise.toml` changes. No hand-built template is saved: the kit is reviewed like any other code. Per-sandbox bootstrap (`make bootstrap`) only installs workspace dependencies.
6. **Lifetime and observability.** Agents are launched with `setsid nohup` inside the sandbox so they outlive the exec session; the dispatcher keeps running sandboxes alive and polls observable repository state (pushed branch, PR, checks, issue comments). Sandboxed agents have no message channel back to the host.
7. **Concurrency.** Host ports are no longer shared, so the single full-stack lock of ADR-0018 § 4 is dropped; the dispatcher still caps concurrent sandboxes by host CPU and memory.
8. "Sandbox" in earlier ADRs, AGENTS.md and task cards again means the agent's sbx sandbox (ADR-0018 § 5 no longer applies).

## Consequences
+ A real isolation boundary: agents no longer run as the owner's OS user, cannot reach the host Docker socket, Keychain or `gh` login, and never hold a GitHub token.
+ Parallel full-stack E2E; no shared caches or ports to coordinate.
− Each sandbox costs VM boot time, disk on the external volume, and its own dependency download; the template keeps this bounded.
− The host-side keepalive is a single point of failure: if it dies, sandboxes idle out and their agents stop (work on disk survives a stop).
− Unattended waves depend on the owner's subscription login: when it expires, dispatching pauses until the owner logs in again.
− sbx is a younger tool than git worktrees; its behaviour is pinned by the version recorded in the probe and rechecked on upgrade.
